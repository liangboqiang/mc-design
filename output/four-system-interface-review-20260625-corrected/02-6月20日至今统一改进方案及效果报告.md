# 统一改进方案及综合效果报告

报告口径：本文件补齐一份“按起始现状本应制定的统一改进方案”，并汇总当前已经形成的综合改进效果  
适用对象：项目汇报、阶段复盘、后续接口和智能体模块优化

## 一、编写说明

这份文件不是单纯写“下一步要怎么做”，而是补齐一个完整口径：

1. 以起始状态为起点，说明当时应该制定什么样的统一改进方案。
2. 按这个统一方案，回看当前阶段已经实际改善了什么。
3. 把改进效果写成可汇报、可量化、可继续验收的形式。

因此，本文件分为两部分：第一部分是“起始阶段应制定的改进方案”，第二部分是“当前综合改进效果”。

## 二、起始现状判断

起始阶段，项目已经具备业务资料和部分工具基础，但从使用和汇报角度看，仍然存在几个突出问题：

| 方面 | 起始现状 | 主要影响 |
| --- | --- | --- |
| 四系统接口 | IPM、QPP、ECMS/ECR、TC 的职责边界还需要统一说明 | 智能体容易选错系统，用户也难判断查的是哪类任务 |
| 工具调用 | 工具能力开始具备，但调用入口和字段规则不够统一 | 容易出现字段漏填、混填、重复尝试 |
| 用户表达 | 用户多用“查任务、打开模板、生成报告”等普通说法 | 智能体需要把普通说法转换成正确系统和正确动作 |
| 结果展示 | 任务、模板、报告、DFMEA 等输出口径不统一 | 用户难确认当前结果是否完整、是否可信 |
| 写入风险 | TC 上传、复制，NX 参数写入和保存等动作会影响真实资料 | 如果没有确认机制，存在误写入风险 |
| 测试闭环 | 测试案例和失败记录还没有形成稳定回归体系 | 改进后难量化说明效果 |
| 汇报材料 | 已有业务案例和资料，但缺少统一的“方案-实施-效果”闭环 | 后续汇报容易显得零散 |

基于这个现状，应当制定一份统一改进方案，把接口分析、工具改造、智能体规则、测试验证和汇报材料放在同一个节奏里推进。

## 三、起始阶段应制定的统一改进方案

### 1. 改进目标

统一改进目标应定义为：让零件设计智能体能够稳定理解用户需求，正确选择 IPM、QPP、ECMS/ECR、TC 四类系统工具，完整展示结果，并在所有会影响真实资料的动作前进行确认。

更通俗地说，就是做到：

1. 用户说得不专业，智能体也能判断该查哪个系统。
2. 用户只给部分信息，智能体能知道还缺什么并追问。
3. 查询出来的任务、模板、变更和资料必须完整展示，不能随意摘要。
4. 一旦要上传、覆盖、复制、保存，必须让用户先确认。
5. 每次改进后都能用测试案例证明效果，而不是只靠主观感觉。

### 2. 改进范围

| 模块 | 改进内容 | 目标结果 |
| --- | --- | --- |
| 四系统接口说明 | 统一 IPM、QPP、ECMS/ECR、TC 的业务边界、输入字段、输出字段、错误影响 | 业务人员能看懂每个系统能做什么 |
| 工具调用规则 | 明确什么时候用哪个工具、哪些字段必填、哪些字段不能混用 | 降低选错工具和填错字段 |
| 任务展示规则 | 固定 IPM 任务表格，完整展示任务编码、任务名称、项目名称、日期、状态 | 用户能准确确认任务 |
| 模板打开规则 | 统一“TC 查候选、NX 打开、WorkPart 确认”的步骤 | 防止查到模板后打不开或误打开 |
| 写入确认规则 | 对 TC 上传、TC 复制、NX 保存、参数写入建立确认表 | 防止误覆盖、误上传、误保存 |
| 运行环境检查 | 查询前检查外部系统连接、运行时、用户身份、NX 状态 | 防止外部系统不可用时输出假结果 |
| 测试和复盘 | 建立七类任务测试案例和失败问题台账 | 每次改进都能量化说明 |

### 3. 计划节奏

| 阶段 | 推进节奏 | 主要任务 | 交付物 |
| --- | --- | --- | --- |
| 第一阶段 | 前期准备 | 梳理四系统能力、统一工具目录、明确字段和调用边界 | 四系统能力说明、工具清单、初版字段规则 |
| 第二阶段 | 集中完善 | 改进智能体调用规则、补充文档包、整理测试案例和业务示例 | 接口分析报告、工具改进方案、测试案例草案、说明书 |
| 第三阶段 | 反馈修正 | 根据真实测试反馈修正关键问题，更新安装包和示例 | TC 模板打开修正、IPM 展示示例、运行时和打包更新 |
| 第四阶段 | 持续验证 | 继续跑七类任务回归测试，形成量化效果报告 | 路由正确率、无效查询拦截率、副作用确认率、证据完整率 |

### 4. 关键改进动作

| 改进动作 | 起始阶段应提出的要求 | 验收方式 |
| --- | --- | --- |
| 四系统入口统一 | 用户需求先分流到 IPM、QPP、ECMS/ECR、TC | 典型问题能选对系统 |
| IPM 展示固定 | 查询结果必须表格展示，任务名称和内容不得缩减 | 表格字段完整率 100% |
| QPP 查询防泛查 | 至少提供一个有效条件才能查 | 空条件拦截率 100% |
| ECMS/ECR 查询防泛查 | 至少提供 ECR 编号、主题、原因、状态、人员、平台或日期之一 | 空条件拦截率 100% |
| TC 模板打开闭环 | TC 只负责查候选，NX 负责打开，打开后确认 WorkPart | 模板误打开和工具误用次数为 0 |
| 写入前确认 | 所有会改真实资料的动作展示确认表 | 副作用确认率 100% |
| 健康检查 | 外部系统不可用时不能用本地示例冒充真实结果 | 失败原因说明率 100% |
| 测试闭环 | 每类问题都沉淀成回归用例 | 七类任务用例持续积累 |

## 四、当前综合改进效果

### 1. 总体效果

当前阶段，项目的改进不是单点变化，而是从“有资料、有部分工具”推进到“工具分类更清楚、文档包更完整、测试反馈能反向修正规则、安装包能同步交付”的状态。

可以概括为四个变化：

1. 从零散能力，变成了按外部系统、TC、NX、报告、DFMEA、本地文件等分类的工具体系。
2. 从只说明“工具能调用”，变成开始说明“什么场景能用、字段怎么填、结果怎么看、失败怎么处理”。
3. 从缺少统一材料，变成形成了多份面向汇报和测试的文档资料。
4. 从发现问题靠人工描述，变成开始把真实测试问题转成规则、示例、安装包和后续回归要求。

### 2. 已形成的主要成果

| 类别 | 当前阶段形成的改进 | 业务效果 |
| --- | --- | --- |
| 工具体系 | 工具按外部系统、TC、NX、报告、DFMEA、本地文件等分类梳理 | 智能体调用边界更清楚，后续更容易拆分七类任务 |
| 四系统说明 | IPM、QPP、ECMS/ECR、TC 的能力和字段逐步清晰 | 用户和汇报对象能理解每个系统分别解决什么问题 |
| 文档资料 | 形成接口分析、工具改进、效果报告、测试案例、架构说明、持续改进等文档包 | 汇报材料从零散说明变为成套资料 |
| 运行上下文 | 用户身份、运行状态、流式输出等问题得到修复和稳定 | 多轮任务中上下文丢失、输出格式异常的问题减少 |
| TC 模板链路 | 根据用户日志定位“模板查到但打开失败”的原因，并调整为 TC 查候选、NX 打开 | 模板打开流程更符合真实业务动作 |
| IPM 展示 | 根据用户反馈补充 IPM 输出示例和展示要求 | 任务编码、任务名称、项目名称、计划日期、状态等字段更容易完整展示 |
| DFMEA 和报告 | 开始处理模板位置、导出文件、图片解密、生成超时等问题 | 交付物生成链路的阻塞点更清晰 |
| 安装交付 | 安装包持续更新，并确认新包包含最新示例和规则 | 改进内容能进入客户端交付，而不是只停留在本地修改 |

### 3. 可量化效果

| 指标 | 起始状态 | 当前状态 | 改进效果说明 |
| --- | --- | --- | --- |
| 工具分类清晰度 | 工具能力已有，但边界不够统一 | 已按外部系统、TC、NX、报告、DFMEA、本地文件等分类 | 从“能调用”提升到“能按任务分类管理” |
| 工具数量覆盖 | 覆盖面不完整或说明不统一 | 当前工具定义达到 55 个左右 | 能力覆盖更完整，但后续重点应转向稳定调用 |
| 文档完整度 | 业务资料和模板已有，但缺少统一包 | 已形成 8 份文档、8 份 PDF、约 29 页渲染结果的文档包 | 汇报和复盘材料明显增强 |
| IPM 展示规则 | 任务内容容易被摘要或字段不全 | 已补充展示示例和“不得缩减”要求 | 用户确认任务的准确性提升 |
| TC 模板打开 | 曾出现查到模板但打开失败 | 已明确问题在调用链路和字段口径，并进行调整 | 从“找不到原因”转为“可按步骤修复和验证” |
| 写入风险识别 | 查询和写入边界不够突出 | 已将上传、复制、保存、参数写入列为需确认动作 | 风险控制意识增强 |
| 测试反馈闭环 | 反馈容易停留在单次问题 | TC、IPM、DFMEA、报告、参数、运行时问题已进入改进清单 | 后续能形成回归测试 |

说明：这些数据用于说明建设量和阶段改善，不等同于生产环境最终指标。生产指标仍需通过七类任务回归测试统一确认。

### 4. 典型问题的改进效果

| 典型问题 | 之前表现 | 现在改善 |
| --- | --- | --- |
| 用户说“查我的任务” | 智能体可能不知道该查什么条件 | 已明确 IPM 查询必须围绕责任人，并要求完整展示任务字段 |
| 查询 QPP | 可能空条件查询或条件无效 | 已明确至少需要责任人、标题、项目编号、日期或状态等有效条件 |
| 查询 ECR | 可能条件过宽，状态字段口径不统一 | 已识别为高优先级待补项，建议补强空条件拦截和字段统一 |
| TC 模板打开 | 查到候选模板后仍打开失败 | 已明确应走“TC 查候选、NX 打开、WorkPart 确认”闭环 |
| 报告/DFMEA 生成 | 模板、导出、解密、超时等问题混在一起 | 已拆成模板路径、数据集导出、解密路由、生成流程等具体问题 |
| 外部查询失败 | 可能退回本地示例数据 | 已明确正式任务中不能把本地示例当真实结果 |

## 五、当前仍需继续完成的事项

| 待完成事项 | 原因 | 建议完成方式 |
| --- | --- | --- |
| ECMS/ECR 空条件拦截 | 目前相比 IPM/QPP 保护不足 | 增加至少一个业务条件的要求 |
| ECMS/ECR 状态字段统一 | 状态字段存在口径差异 | 对外只保留一个“流程状态”说法，内部做映射 |
| IPM 展示最终验收 | 已补充示例，但还需用真实任务验证 | 用用户测试记录复测任务名称是否完整展示 |
| TC 写入确认表 | 风险已识别，但需要固化为流程 | 上传、覆盖、复制、保存前统一弹出确认内容 |
| 运行时健康检查 | 避免外部系统不可用时输出假结果 | 查询前检查运行时、连接、身份和系统地址 |
| 七类任务回归测试 | 需要量化证明效果 | 建立固定用例并记录通过率、失败原因和修复项 |

## 六、建议汇报话术

起始阶段，项目已经具备一定的业务资料和工具基础，但四大系统接口、工具调用规则、展示口径和测试闭环还没有形成统一方案。按照现在补齐的方案，项目应围绕“选对系统、填对字段、完整展示、写入前确认、测试可量化”五个目标推进。

经过当前阶段的集中改进，平台已经从零散工具和材料，推进到分类清晰的工具体系和成套文档资料；IPM、QPP、ECMS/ECR、TC 的职责边界更清楚；TC 模板打开、IPM 任务展示、报告和 DFMEA 生成等真实反馈已进入改进闭环；安装包也已经跟随更新。下一步重点不是继续堆功能，而是补齐 ECR 查询保护、TC 写入确认、运行时健康检查和七类任务回归测试，用数据证明智能体调用工具的准确率、稳定性和交付风险控制能力。
