# 四大系统接口能力分析报告

编写日期：2026年6月25日  
分析范围：IPM、QPP、ECMS/ECR、TC 四类系统接口能力，以及智能体调用这些能力时需要关注的输入、输出和业务影响  
表达口径：面向业务汇报，尽量少用技术语言，重点说明“能做什么、要填什么、填错会怎样、后续怎么改”

## 一、总体结论

四大系统在零件设计智能体中的角色已经比较清楚：IPM 用来找设计任务，QPP 用来找质量计划，ECMS/ECR 用来找变更任务，TC 用来查模板、打开资料、导出和回传交付物。四个系统不是互相替代的关系，而是共同支撑一个完整设计流程。

从目前材料看，最大问题不是“系统没有接口”，而是智能体在调用时容易出现三类偏差：

1. 用户说的是普通业务话术，智能体需要判断到底该查 IPM、QPP、ECMS/ECR 还是 TC。
2. 每个系统字段含义不同，任务名称、项目名称、ECR 编号、TC 图号不能混填。
3. 查询类动作和写入类动作风险不同，查询可以快速执行，上传、覆盖、复制、保存等动作必须先确认。

因此，本报告的重点不是罗列程序细节，而是把四个系统的工具能力讲清楚，并把正确填写和错误填写的影响讲清楚，作为后续接口模块优化和汇报材料的基础。

## 二、四大系统在业务流程中的位置

| 系统 | 普通理解 | 在零件设计智能体中的作用 | 常见使用场景 |
| --- | --- | --- | --- |
| IPM | 设计任务清单 | 找到“要做哪条设计任务” | 查询我的任务、确认任务名称、项目名称、计划完成时间、任务状态 |
| QPP | 质量计划清单 | 找到“质量计划里安排了什么动作” | 按责任人、标题、项目编号、日期或状态查询质量计划 |
| ECMS/ECR | 变更任务清单 | 找到“为什么改、改什么、谁负责、涉及哪些平台” | 查询 ECR 编号、变更主题、变更原因、责任人、产品平台 |
| TC | 受控资料库 | 找模板、模型、图纸、数据集，并回传正式交付物 | 查模板库、打开模型、导出文件、上传设计说明书或 DFMEA |

一句话概括：IPM 告诉智能体“任务从哪里来”，QPP 告诉智能体“质量计划怎么约束”，ECMS/ECR 告诉智能体“变更背景是什么”，TC 告诉智能体“资料和结果在哪里受控管理”。

## 三、IPM 接口能力分析

IPM 主要用于查询设计任务。智能体开始执行设计任务前，必须先把任务查清楚，不能凭用户一句“帮我做连杆任务”就直接进入建模或报告生成。

| 项目 | 说明 |
| --- | --- |
| 能提供的能力 | 查询设计任务列表，返回任务编码、任务名称、项目名称、计划完成日期、状态、责任人、零件信息和附件线索 |
| 关键入参 | 责任人工号或责任人姓名至少一个；项目名称；项目编码；任务名称；确认状态；计划完成日期范围；分页信息 |
| 关键出参 | 任务编码、任务名称、项目名称、任务状态、计划开始/完成日期、责任人、图号、零件号、零件名称、附件链接、总数 |
| 正确填写效果 | 能找到责任人名下符合条件的真实设计任务，并让用户确认要执行哪一条 |
| 错误填写影响 | 不填责任人会无法查询；把项目名称填成任务名称可能查不到；任务名称被摘要会影响用户确认；条件太宽会查出太多无关任务 |

建议在智能体展示 IPM 任务时固定使用表格，并保证至少包含：任务编码、任务名称或完整任务内容、项目名称、计划完成日期、状态、责任人。用户反馈已经明确要求“任务名称内容不得缩减展示”，因此这里应作为强制规则。

## 四、QPP 接口能力分析

QPP 主要用于查询质量管理详细计划。它和 IPM 不同，IPM 更偏“设计任务”，QPP 更偏“质量计划动作和完成要求”。

| 项目 | 说明 |
| --- | --- |
| 能提供的能力 | 查询质量计划明细，查看责任人、责任部门、计划标题、要求完成时间、实际完成时间、状态、关联编号和附件 |
| 关键入参 | 要求完成时间范围、实际完成时间范围、责任人、责任部门、计划标题、项目编号、关联编号、SDM 编号、计划状态 |
| 关键出参 | 计划 ID、标题、完成时间、责任人、责任部门、执行记录、状态、附件、关联编号、子计划数量 |
| 正确填写效果 | 能按责任人、项目编号、标题或时间范围定位质量计划动作 |
| 错误填写影响 | 只填“是否按工号解释”没有实际筛选作用；责任人姓名和工号混用会查不到；状态值填错会查偏；完全不填筛选条件会形成无效查询 |

QPP 查询建议至少提供一个有效业务条件，例如责任人、计划标题、项目编号、日期范围或状态。不能只让智能体“查一下 QPP”，否则范围太大，结果不可控。

## 五、ECMS/ECR 接口能力分析

ECMS/ECR 主要用于查询变更任务，帮助智能体了解设计变更的背景、原因、责任人和影响范围。它不等同于 IPM 设计任务，也不等同于 TC 模板资料。

| 项目 | 说明 |
| --- | --- |
| 能提供的能力 | 查询 ECR 变更任务，查看变更主题、变更原因、流程状态、申请人、责任人、产品平台、计划完成日期和涉及机型 |
| 关键入参 | ECR 编号、变更主题、更改原因、流程状态、创建日期范围、计划完成日期范围、申请人、责任人、部门、板块、产品平台、分页信息 |
| 关键出参 | ECR 列表、总数、ECR 编号、变更主题、更改原因、流程状态、申请人、责任人、部门、计划完成日期、产品平台、涉及机型 |
| 正确填写效果 | 能找到与当前设计任务相关的变更背景，帮助判断设计目标、限制条件和交付要求 |
| 错误填写影响 | 不给任何筛选条件会产生大范围查询；把项目名称当 ECR 编号会查不到；分页数量填错会误以为没有结果；状态字段口径不统一会导致状态过滤不生效 |

ECMS/ECR 后续应补齐“空条件拦截”和“状态字段统一”。这项工作对业务影响很直接：防止智能体查到一堆不相关变更，或者看似按状态查了，实际没有过滤成功。

## 六、TC 接口能力分析

TC 是受控资料库，既有查询，也有真实写入。它的风险比 IPM、QPP、ECMS 查询更高，因为上传、覆盖、复制、保存等动作会影响正式资料。

| 能力类型 | 能做什么 | 关键入参 | 关键出参 | 填错影响 |
| --- | --- | --- | --- | --- |
| 模板查询 | 查智能体模板库里的参数化模板或三维模型模板 | 文件夹名称、所有者、图号或名称线索 | 模板候选、图号、版本、发布状态 | 查不到模板，或把候选当成已打开模型 |
| 子级查询 | 查看某个版本下有哪些模型、图纸或数据集 | 图号、版本、所有者 | 子对象、数据集、模型或图纸信息 | 版本错会影响后续打开和交付 |
| 属性查询 | 查询分类属性、流程人员等信息 | 图号、版本 | 分类属性、校对/审核/批准人员 | 报告信息不准确 |
| 文件导出 | 把 TC 里的 Excel、Word、PDF 等导出到本地 | 数据集 ID、保存路径、是否覆盖 | 本地文件路径、文件信息 | 路径不清会影响后续读取；覆盖策略错会覆盖已有文件 |
| 文件上传 | 上传设计说明书、DFMEA 等文件 | 图号、版本、文件名、文件内容、是否覆盖 | 上传结果、状态、消息 | 会改变真实 TC 数据，目标或覆盖策略错会造成交付错误 |
| 复制创建 | 复制已有对象形成新对象 | 原对象图号/版本、新对象编号、所有者 | 新对象编号、版本、创建结果 | 新编号错会产生错误对象 |

TC 工具必须区分三个状态：

1. 候选：系统查到了可选模板或对象，但还没有打开。
2. 已打开：模型或图纸已经被工具打开。
3. 已确认：当前工作对象已经确认无误，可以进入参数、报告或回传。

只有到“已确认”状态，才允许继续执行参数写入、保存、上传和复制等动作。

## 七、字段填写正确或错误的综合影响

| 填写情况 | 业务表现 | 对后续流程的影响 |
| --- | --- | --- |
| 系统选对、字段填对 | 能查到正确任务、计划、变更或资料 | 后续设计、建模、报告、DFMEA 和回传可以继续 |
| 系统选错 | 用户想查设计任务，却查了变更或 TC 资料 | 结果不相关，后续流程从一开始就偏掉 |
| 关键字段缺失 | 查询被拒绝，或返回范围过大 | 用户需要反复补充信息，效率下降 |
| 字段混用 | 项目名、任务名、ECR 编号、TC 图号混在一起 | 查不到、查偏，甚至打开错误对象 |
| 写入前未确认 | 上传、覆盖、复制、保存直接执行 | 可能影响正式资料，风险最高 |
| 返回结果被摘要 | 用户看不到完整任务内容或完整状态 | 无法判断是否选中了正确任务 |

## 八、后续接口模块改进方向

| 改进方向 | 目标 | 优先级 |
| --- | --- | --- |
| 四系统入口规则 | 让智能体先判断用户要查哪个系统 | 高 |
| 字段字典统一 | 让普通话和系统字段稳定对应 | 高 |
| IPM 完整展示 | 任务名称和任务内容不再被压缩或改写 | 高 |
| ECMS/ECR 空条件拦截 | 防止大范围无效查询 | 高 |
| TC 写入前确认 | 防止误上传、误覆盖、误复制 | 高 |
| 运行时健康检查 | 防止外部系统不可用时拿本地示例冒充真实结果 | 中高 |
| 七任务回归测试 | 每次调整后能量化验证是否变好 | 中高 |

## 九、汇报用结论

截至目前，四大系统接口能力已经具备进入统一治理的条件。IPM、QPP、ECMS/ECR、TC 各自承担不同业务角色，后续不应继续简单堆工具，而应重点解决“智能体选对系统、填对字段、完整展示结果、写入前确认、全过程留痕”这五件事。

如果按上述方向改进，后续汇报可以从“已经做了哪些工具”转向“工具调用准确率提升了多少、无效查询拦截了多少、交付风险降低了多少、用户能否看懂和复核结果”。
