# 智能体工具持续改进方案及阶段效果报告

报告口径：本文件按“先统一靶子，再归并动作”的方式编写。也就是说，把 mc-design 已经实施的多项改进，统一归到一套本应在起始阶段制定的持续改进方案中，并说明这些动作已经带来的阶段效果。

适用对象：阶段汇报、接口模块优化复盘、智能体工具调用治理评审。

## 一、方案定位

本方案不是泛泛写“以后要优化”，而是针对起始阶段暴露出的不足，倒推一套完整的改进靶子。方案核心是：

- 把零散工具变成分工明确的工具体系；
- 把普通用户话术转换成正确任务入口；
- 把 TC、NX、参数、报告、DFMEA 的先后关系管住；
- 把所有有风险的写入动作放到确认门禁后面；
- 把每次问题转成可复测、可量化的改进记录。

最终目标是让 mc-design 从“能调用很多工具”，提升为“能按零件设计流程稳定推进任务”。

## 二、统一改进目标

| 改进目标 | 普通解释 | 验收口径 |
| --- | --- | --- |
| 入口选对 | 用户说“查任务、查计划、查变更、找模板”时，智能体能选对系统 | 典型测试问题中，首轮入口判断正确率达到 80% 以上，两轮优化后达到 90% 以上 |
| 字段填对 | 责任人、任务名、项目名、变更编号、TC 图号不混填 | 无效查询能被拦截或追问 |
| 内容完整 | 任务名称、任务内容、模板候选、状态不被随意摘要 | IPM 等关键结果固定字段完整展示 |
| 状态清楚 | 候选、已打开、已确认三个状态不混用 | 未确认 WorkPart 前不进入参数写入 |
| 参数有证据 | 参数来源于任务文本、参考公式、词典和 NX 真实表达式 | 没有来源或有冲突时暂停 |
| 写入先确认 | NX 写入、保存、TC 上传、复制都先让用户确认 | 有副作用动作确认率达到 100% |
| 交付可追溯 | 报告、DFMEA、截图等能说明文件位置和校验结果 | 正式交付证据完整率达到 95% 以上 |
| 问题可复测 | 每类问题都有固定案例和结果记录 | 七类任务持续进入回归测试 |

## 三、针对起始不足的改进方案和已形成效果

| 起始不足 | 持续改进方案 | 已形成的改进动作 | 阶段效果 |
| --- | --- | --- | --- |
| 工具多但入口不清 | 建立主智能体和子智能体分工，主智能体只负责理解、分派和汇总 | 已形成 1 个主智能体、7 个业务子智能体的分工；工具按外部系统、TC、NX、报告、DFMEA、本地文件等分类 | 智能体不再把所有事情混在一个入口里处理，后续可以按任务类型验收 |
| 四大系统容易混用 | 建立 IPM、QPP、ECMS/ECR、TC 的业务边界和字段规则 | IPM 用于设计任务，QPP 用于质量计划，ECMS/ECR 用于变更背景，TC 用于受控资料；运行时身份用于“我的任务”查询 | 用户不用说工具名，也能由智能体选择正确系统 |
| IPM 任务展示不完整 | 固定任务候选展示格式，保留任务原文 | 已补充 IPM 标准展示规则，要求任务编码、任务名称或任务内容、项目名称、计划完成信息、状态完整展示 | 用户能看清任务内容，避免选错任务或提前进入错误流程 |
| 本地工具和连接器可见性不稳定 | 让外部系统连接器、本地工具目录和运行时身份进入统一运行上下文 | 连接器工具被纳入可见性检查；运行时用户身份进入任务查询；会话记录开始保留关键过程 | “本地能不能看到工具、用了哪个身份、为什么失败”可以被检查 |
| TC 模板和 NX 打开状态混淆 | 固化“TC 查候选、NX 打开、WorkPart 确认”的三步法 | TC 模板候选不再直接当成已打开模型；模板打开改由 NX 工具执行；打开后读取 WorkPart 信息确认 | 模板链路从“查到就算完成”变为“打开并确认后才进入参数阶段” |
| 参数识别和写入计划不稳 | 建立参数识别、公式来源、词典映射、NX 表达式读取、写入计划草案的顺序 | 参数智能体只生成证据和写入计划，不直接写模型；参考 Excel、公式校验、真实表达式检查进入流程；中文参数名不能直接进入写入计划 | 由“猜参数、直接写”转为“先证明、再确认、后执行” |
| 写入类动作风险高 | 把 NX 写入、保存、TC 上传、复制、覆盖统一纳入确认门禁 | 主智能体要求用用户确认处理副作用；TC 上传、复制和 NX 写入都被列为确认后动作；自动出图等高风险入口被收敛 | 降低误写、误传、误覆盖正式资料的风险 |
| 报告和 DFMEA 交付不稳 | 把模板检查、证据收集、文件校验和结果返回做成固定链路 | 设计报告增加图片解密通道；DFMEA 增加模板资源、数据集导出和工作簿校验；报告输出要求返回文件路径、大小、版本和缺口 | 交付物从“说已生成”变成“能找到、能校验、能复核” |
| 运行时和安装包不够闭环 | 强化本地客户端、运行依赖、日志、安装包自检和安全暴露面 | 安装包持续更新；运行时打包补齐依赖；移除不应暴露的本地命令入口；会话日志做精简和摘要 | 客户端交付更可控，测试人员能更快定位是环境、接口还是流程问题 |
| 效果难汇报 | 建立文档包、测试案例和量化指标 | 已形成 8 份文档、8 份 PDF、成套页面渲染结果；七类任务测试案例矩阵进入资料包 | 汇报从“做了很多改动”转为“围绕哪些问题、如何验收、效果如何证明” |

## 四、工具体系的阶段性变化

现阶段工具体系已经可以按业务类型拆开理解：

| 工具类别 | 数量 | 主要作用 | 对用户的价值 |
| --- | --- | --- | --- |
| 外部系统工具 | 3 | 查询 IPM、QPP、ECMS/ECR | 找到任务、计划和变更背景 |
| Teamcenter 工具 | 8 | 查模板、查子对象、导出数据集、上传文件、复制对象 | 管住受控资料和交付物 |
| NX 工具 | 22 | 打开模型、读取参数、修改参数、截图、视图操作 | 支撑本地建模和验证 |
| 报告工具 | 9 | 模板检查、证据收集、生成、更新、查询、图片解密 | 支撑设计说明书交付 |
| DFMEA 工具 | 6 | 模板选择、风险计算、填表、校验 | 支撑 DFMEA 表自动编写 |
| 本地文件和异步任务工具 | 6 | 文件读写、复制、异步执行长任务 | 支撑大文件和长流程处理 |
| MySQL 查询工具 | 1 | 查询参数词典 | 支撑参数识别和映射 |

汇总看，工具能力已经覆盖 55 个左右的具体工具入口，并配套 8 个智能体角色和 15 个技能说明。这个变化说明 mc-design 已经从单点工具，转向按业务模块组织工具。

## 五、七类任务的持续改进闭环

持续改进不应只看单个接口，而应按七类任务持续复测：

| 任务类型 | 持续改进重点 | 验收方式 |
| --- | --- | --- |
| 任务入口 | IPM、QPP、ECMS/ECR 分流正确，候选完整展示 | 用户能选中正确任务，候选不被摘要 |
| 模板准备 | TC 候选、NX 打开、WorkPart 确认分开 | 未确认 WorkPart 前不进入参数阶段 |
| 参数方案 | 边界参数、设计参数、公式来源、NX 表达式全部说清楚 | 有冲突或缺口时暂停并追问 |
| 建模和回传 | 写入前确认，写入后回读，上传前确认 | 有副作用动作确认率 100% |
| 图纸处理 | 只处理受控图纸查看和确认，不自动创建危险结果 | 没有候选不猜图纸，不自动上传 |
| DFMEA | 先选模板，再填表，再校验 | 没有校验结果不称为正式交付 |
| 设计报告 | 先查模板槽位，再收集证据，再生成文件 | 文件路径、大小、版本、缺口记录完整返回 |

## 六、阶段效果和量化说明

| 评估项 | 起始状态 | 阶段效果 | 后续验收口径 |
| --- | --- | --- | --- |
| 工具组织 | 工具能力分散，入口容易混用 | 已按 7 类工具组、8 个智能体角色组织 | 检查用户问题是否能稳定路由到正确子智能体 |
| 任务查询 | IPM、QPP、ECR 都有能力，但规则不够统一 | IPM 展示和运行时身份规则已补强，QPP 外部不可用能分类说明，ECR 保护项已纳入改进靶子 | 无效查询拦截率目标 100% |
| 模板链路 | TC 查到候选后容易被当成可建模 | 已改为 TC 查候选、NX 打开、WorkPart 确认 | 模板误推进次数为 0 |
| 参数处理 | 可能用中文名或经验判断生成写入计划 | 已要求先查公式、参数词典和 NX 真实表达式；写入计划只是草案 | 缺少来源时不输出可执行写入 |
| 交付物 | 报告、DFMEA、截图证据不够稳定 | 报告图片解密、DFMEA 模板和校验、文件证据规则已补强 | 交付证据完整率目标 95% 以上 |
| 安全门禁 | 写入、上传、复制等动作风险边界不够突出 | 副作用动作统一归入用户确认流程，高风险入口被收敛 | 写入前确认率目标 100% |
| 文档和测试 | 汇报材料容易零散 | 已形成 8 份文档、8 份 PDF 和七类任务测试案例矩阵 | 后续每次改动按同一矩阵复测 |
| 阶段测试记录 | 问题主要靠人工描述 | 已有多组阶段测试记录，客户端侧曾形成百项以上用例通过记录，业务适配工具链也形成 185 项通过记录 | 继续按测试记录说明通过、失败和阻塞原因 |

这些数字的意义不是宣称所有问题已经结束，而是说明项目已经具备按统一口径持续验收的基础：工具有分类，任务有矩阵，交付有证据，失败能归类。

## 七、后续纳入闭环的重点项

| 重点项 | 为什么要纳入闭环 | 建议验收方式 |
| --- | --- | --- |
| ECMS/ECR 空条件保护 | 变更查询如果条件过宽，会影响后续判断 | 至少一个有效业务条件才允许查询 |
| ECMS/ECR 状态口径统一 | 状态字段不统一会造成筛选偏差 | 对外只展示统一的“流程状态” |
| QPP 外部可用性复测 | 外部超时不应误判为智能体逻辑失败 | 单独记录为外部接口状态，并在恢复后复测 |
| TC 真实上传和复制验证 | 这类动作影响正式资料，必须谨慎验收 | 在具备凭据和网络前置后，用确认表逐项验证 |
| NX 截图和图纸链路 | 报告和图纸需要真实文件证据 | 每张截图记录视图、路径、大小和校验信息 |
| 七类任务回归矩阵 | 单点修复不能代表全流程变好 | 每次规则变更后重跑相关案例和全量案例 |
| 客户端运行时健康检查 | 安装包、端口、运行依赖会影响真实体验 | 启动后自动检查本地服务、工具清单和连接状态 |

## 八、汇报用结论

起始阶段的问题不在于 mc-design 没有能力，而在于能力分散、入口不稳、状态不清、证据不足、写入风险没有统一管控。持续改进方案把这些不足统一到一条业务链路上：先选对系统，再确认任务，再准备模板，再形成参数方案，再执行受控写入，最后生成可追溯的报告和 DFMEA。

阶段效果已经体现为工具体系更清楚、子智能体边界更明确、IPM 展示更完整、TC/NX 模板链路更可靠、参数方案更强调证据、报告和 DFMEA 交付更可追溯、安装包和运行时更可检查。后续只要继续按七类任务矩阵复测，就能把改进效果从“感觉变好”变成“有指标、有证据、可复盘”的汇报材料。
