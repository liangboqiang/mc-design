# 智能体调用工具持续改进方案及阶段性成效报告

报告定位：本报告用于说明零部件设计智能体围绕工具调用、任务分流、模板处理、参数设计、交付物生成和运行交付所采取的持续改进措施，并总结当前已形成的阶段性成效。

## 一、改进目标

本阶段改进的总体目标，是让智能体从“具备工具调用能力”提升为“能够按零部件设计流程稳定完成任务”。具体包括：

1. 用户提出普通业务需求后，智能体能够判断应进入哪个业务环节。
2. 查询外部系统时，能够使用正确字段，并在信息不足时主动追问。
3. 查询结果必须完整展示，方便用户确认任务、模板或变更信息。
4. 跨 TC、NX、报告和 DFMEA 的流程必须有清晰状态，不提前推进。
5. 涉及写入、保存、上传、复制等动作前，必须先让用户确认。
6. 最终交付物必须有文件证据和检查结果，便于验收和复盘。

## 二、持续改进思路

持续改进不是简单增加工具数量，而是围绕业务流程建立一套稳定机制：

- 第一，先把任务入口理清楚，避免 IPM、QPP、ECMS/ECR、TC 混用。
- 第二，把工具能力分类，让每个智能体只处理自己负责的业务。
- 第三，把候选、已打开、已确认等状态说清楚，避免流程跳步。
- 第四，把参数、模型、报告、DFMEA 的证据链补齐。
- 第五，把测试问题沉淀为规则、示例和回归案例。

按照这个思路，平台改进不再是零散修补，而是围绕任务入口、模板准备、参数方案、建模回传、图纸处理、DFMEA、设计报告七类任务持续推进。

## 三、主要改进措施

| 改进方向 | 采取的措施 | 已形成效果 |
| --- | --- | --- |
| 智能体分工 | 明确主智能体负责理解需求和分派任务，业务子智能体分别负责任务查询、模板准备、参数处理、建模、图纸、DFMEA 和报告 | 流程边界更清楚，减少一个智能体同时处理所有事项造成的混乱 |
| 工具分类 | 按外部系统、TC、NX、报告、DFMEA、本地文件、参数词典等类别整理工具 | 工具调用范围更清晰，便于后续按模块测试和汇报 |
| 任务入口 | 强化 IPM、QPP、ECMS/ECR 的使用边界，默认结合运行身份查询当前用户任务 | 用户说“我的任务”时，智能体能更自然地进入正确任务入口 |
| IPM 展示 | 固定任务候选展示内容，要求保留任务名称或任务内容原文 | 用户可以更准确地确认任务，避免因摘要导致误选 |
| TC/NX 衔接 | 明确 TC 查询只是候选，NX 打开并确认当前工作对象后才进入参数阶段 | 降低“查到模板但未真正打开模型”的流程风险 |
| 参数处理 | 增加参数识别、参考公式、参数词典、NX 实际表达式和写入计划的顺序要求 | 参数方案更强调来源和确认，避免直接用中文名称或经验值写入模型 |
| 写入门禁 | 将 NX 写入、模型保存、TC 上传、复制和覆盖纳入确认流程 | 降低误写、误传、误覆盖正式资料的风险 |
| 报告生成 | 补强设计说明书模板检查、证据收集、图片处理和文件结果返回要求 | 报告生成从“生成文本”转向“形成可验收文件” |
| DFMEA 生成 | 补充 DFMEA 模板选择、填表、校验和文件证据规则 | DFMEA 交付链路更完整，便于后续复核 |
| 运行交付 | 强化本地运行时、安装包、工具可见性、会话记录和运行依赖检查 | 测试和部署问题更容易定位，减少“环境问题”和“工具问题”混在一起 |

## 四、阶段性成效

### 1. 工具体系更加清晰

当前工具能力已按业务类型形成较清楚的分类，覆盖外部系统查询、Teamcenter、NX、本地文件、设计报告、DFMEA 和参数词典等方向。

| 类别 | 数量 | 业务作用 |
| --- | --- | --- |
| 外部系统工具 | 3 | 查询 IPM、QPP、ECMS/ECR |
| Teamcenter 工具 | 8 | 查询模板、导出数据集、上传文件、复制对象 |
| NX 工具 | 22 | 打开模型、读取参数、修改参数、截图和视图操作 |
| 设计报告工具 | 9 | 模板检查、证据收集、生成、更新、查询和图片处理 |
| DFMEA 工具 | 6 | 模板选择、风险计算、填表和校验 |
| 本地文件与异步任务工具 | 6 | 文件读写、复制和长任务处理 |
| 参数词典查询工具 | 1 | 支撑参数识别和映射 |

整体看，工具数量已覆盖约 55 项具体能力，说明平台已经具备支撑完整业务流程的基础。

### 2. 智能体职责更加明确

平台已形成主智能体加多个业务子智能体的组织方式。主智能体不直接处理所有外部系统和工具，而是根据用户意图分派到相应业务智能体。这样可以减少越权调用和流程混乱，也便于后续按任务类型进行测试。

### 3. 任务查询展示更加规范

IPM 任务查询已经明确要求完整展示任务编码、任务名称或任务内容、项目名称、计划完成信息和状态。这个改进对业务非常关键，因为用户只有看清任务内容，才能判断后续应进入参数分析、模板选择还是报告流程。

### 4. TC 与 NX 链路更加符合真实业务

模板处理已从“查到候选”进一步规范为“查候选、打开模型、确认当前工作对象”。这能够避免把 TC 查询结果直接当成 NX 可操作模型，也让后续参数写入和报告生成有更可靠的基础。

### 5. 参数方案更加重视依据

参数处理已经从简单字段匹配，逐步转向任务文本识别、参考资料核对、参数词典查询、NX 实际表达式确认和写入计划生成。对于缺少依据、存在冲突或信息不完整的情况，要求暂停并让用户确认。

### 6. 报告和 DFMEA 交付能力得到加强

设计说明书和 DFMEA 不再只关注内容生成，还开始强调模板检查、文件生成、文件校验、图片处理、缺口记录和交付证据。这有助于后续把“智能体生成结果”转化为“可以验收和归档的交付文件”。

### 7. 文档和测试材料更加成套

项目已形成围绕接口分析、工具改进、效果说明、测试案例、架构说明和持续改进的成套资料。当前资料包包括 8 份文档、8 份 PDF 以及配套页面渲染结果，可用于阶段复盘、汇报和后续测试参考。

## 六、后续改进建议

| 建议方向 | 主要原因 | 建议做法 |
| --- | --- | --- |
| 强化 ECMS/ECR 查询保护 | 变更查询条件过宽会返回无关信息 | 增加有效条件检查，统一流程状态口径 |
| 持续复测 QPP 可用性 | QPP 受外部系统状态影响明显 | 将外部不可用和智能体逻辑问题分开记录 |
| 固化写入前确认表 | 写入和上传会影响正式资料 | 对 NX 写入、TC 上传、复制、覆盖建立统一确认项 |
| 完善 TC 真实回传验证 | 回传动作需要真实凭据和网络环境 | 在具备条件后验证文件、版本、覆盖策略和返回结果 |
| 加强截图和图纸证据 | 报告和图纸需要可复核文件 | 记录截图视图、路径、文件大小和校验信息 |
| 建立固定回归矩阵 | 单次修复不能代表全流程稳定 | 每次修改规则或工具后，按七类任务重跑相关案例 |
| 完善运行健康检查 | 安装包、端口、运行依赖会影响用户体验 | 启动后检查本地服务、工具清单、外部连接和登录身份 |

## 七、汇报结论

本阶段改进已经使零部件设计智能体从零散工具调用，逐步转向按业务流程组织能力。四大系统入口更加清晰，任务展示更加规范，TC 与 NX 的衔接更符合真实业务，参数处理更强调依据和确认，报告与 DFMEA 交付更重视文件证据。

后续应继续围绕七类任务开展复测和优化，把每一次问题反馈转化为规则、示例、测试案例和验收指标。这样，平台改进效果才能从“功能增加”转化为“业务流程更稳定、交付风险更可控、汇报材料更有依据”。
