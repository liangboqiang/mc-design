# 四大系统接口应用现状与问题分析报告

报告定位：本报告用于说明 IPM、QPP、ECMS/ECR、TC 四类系统在零部件设计智能体中的业务作用、接口能力、关键输入输出、前期应用中暴露的主要问题，以及对后续接口模块优化的建议。

## 一、总体结论

零部件设计智能体已经具备连接企业任务、质量计划、变更信息和受控资料的基础能力。IPM、QPP、ECMS/ECR、TC 四类系统分别承担不同角色：IPM 负责设计任务入口，QPP 负责质量计划约束，ECMS/ECR 负责变更背景说明，TC 负责模板、模型、图纸和交付文件的受控管理。

前期主要问题不是单个系统不可用，而是多系统协同时需要进一步规范：用户表达方式比较口语化，智能体需要先判断应进入哪个系统；不同系统字段含义不同，不能把任务名称、项目名称、变更编号、图号混用；查询动作和写入动作风险不同，凡是会影响真实资料的动作都必须先确认。

因此，后续改进重点应放在“系统入口判断、字段填写规范、结果完整展示、跨系统状态确认、写入前确认、交付证据留存”六个方面。

## 二、四大系统业务定位

| 系统 | 业务定位 | 智能体中的作用 | 典型场景 |
| --- | --- | --- | --- |
| IPM | 设计任务管理 | 确认当前要处理的设计任务 | 查询我的任务、查看未提交任务、确认任务编码和任务内容 |
| QPP | 质量计划管理 | 确认质量计划要求和责任安排 | 查询质量计划、责任人计划、计划状态和完成要求 |
| ECMS/ECR | 设计变更管理 | 了解变更原因、变更主题和影响范围 | 查询 ECR 编号、变更主题、责任人、涉及机型 |
| TC | 受控资料管理 | 管理模板、模型、图纸、数据集和交付文件 | 查模板、打开模型、导出资料、上传说明书或 DFMEA |

四类系统之间不是替代关系，而是共同支撑一个完整流程：先确认任务，再确认模板和资料，再开展参数设计和模型处理，最后形成报告、DFMEA 和回传资料。

## 三、接口能力和输入输出分析

### 1. IPM 设计任务接口

IPM 主要用于获取设计任务。智能体在进入建模、参数分析或报告生成前，应先通过 IPM 确认任务来源。

| 项目 | 内容 |
| --- | --- |
| 可提供能力 | 查询设计任务列表，返回任务编码、任务名称或任务内容、项目名称、状态、责任人、零件信息和附件线索 |
| 关键输入 | 责任人工号或姓名、任务关键词、项目名称、项目编码、任务状态、计划完成范围 |
| 关键输出 | 任务编码、任务名称或任务内容、项目名称、计划完成信息、责任人、确认状态、零件图号、附件线索 |
| 正确填写效果 | 能找到责任人名下符合条件的设计任务，并让用户确认要处理哪一条 |
| 填写错误影响 | 责任人缺失会导致无法准确查询；项目名称和任务名称混填会导致查不到或查偏；任务内容展示不完整会影响用户确认 |

IPM 的关键要求是“任务内容必须完整展示”。如果任务内容被缩短，用户无法判断任务是直接修改参数，还是需要先做边界参数换算。

### 2. QPP 质量计划接口

QPP 主要用于查询质量计划，帮助智能体理解计划约束、责任安排和完成要求。

| 项目 | 内容 |
| --- | --- |
| 可提供能力 | 查询质量计划明细，返回计划标题、责任人、责任部门、完成要求、状态、关联编号和附件信息 |
| 关键输入 | 责任人、责任部门、计划标题、项目编号、关联编号、完成范围、计划状态 |
| 关键输出 | 计划标题、责任人、部门、状态、计划完成要求、执行记录、附件信息 |
| 正确填写效果 | 能定位到与当前任务相关的质量计划要求 |
| 填写错误影响 | 空条件或无效条件会导致查询范围过大；姓名、工号、项目编号混用会影响查询结果；外部系统不可用时需要明确说明原因 |

QPP 的重点不是替代 IPM，而是补充质量计划要求。智能体不能因为 IPM 查不到，就直接把 QPP 结果当成设计任务。

### 3. ECMS/ECR 变更任务接口

ECMS/ECR 主要用于查询设计变更背景，说明为什么改、改什么、谁负责、涉及哪些范围。

| 项目 | 内容 |
| --- | --- |
| 可提供能力 | 查询变更任务，返回变更主题、变更原因、流程状态、责任人、申请部门、产品平台和涉及机型 |
| 关键输入 | ECR 编号、变更主题、变更原因、流程状态、责任人、申请人、部门、产品平台 |
| 关键输出 | 变更编号、主题、原因、状态、责任人、部门、计划信息、影响范围 |
| 正确填写效果 | 能为后续设计判断提供变更背景和约束条件 |
| 填写错误影响 | 把项目名称当成 ECR 编号会查不到；查询条件过宽会返回无关变更；状态口径不统一会影响筛选准确性 |

ECMS/ECR 后续应重点加强空条件保护和状态口径统一，避免智能体返回大量无关变更信息。

### 4. TC 受控资料接口

TC 是模板、模型、图纸和交付物的受控资料来源，也是风险最高的接口类别之一。

| 项目 | 内容 |
| --- | --- |
| 可提供能力 | 查询模板和资料、查看版本子对象、导出数据集、上传文件、复制对象 |
| 关键输入 | 文件夹、所有者、图号、版本、数据集、文件名、文件内容、覆盖策略 |
| 关键输出 | 模板候选、版本信息、模型或图纸对象、导出文件、上传或复制结果 |
| 正确填写效果 | 能找到正确模板和受控资料，并支撑后续建模、报告和回传 |
| 填写错误影响 | 图号或版本错误会打开错误对象；把候选当成已打开模型会导致后续流程失真；上传或覆盖前不确认会影响正式资料 |

TC 查询结果只能作为候选。只有模型已经在 NX 中打开，并读取到当前工作对象信息后，才能进入参数和建模阶段。

## 四、前期应用中的主要问题

### 1. 多系统入口判断不够稳定

用户通常不会按系统名称表达需求，而是说“查我的任务”“看一下变更”“找模板”“生成报告”。如果智能体不能准确判断入口，就会出现设计任务、质量计划、变更任务和受控资料混用的问题。

### 2. 关键字段容易混填

IPM 的任务名称、QPP 的计划标题、ECR 的变更编号、TC 的图号和版本含义不同。字段混填会造成查不到、查偏或进入错误流程。

### 3. 查询结果展示不够统一

任务候选必须让用户能看懂并确认。前期尤其需要解决 IPM 任务名称或任务内容被压缩展示的问题。任务内容一旦不完整，后续参数判断、模板选择和报告编写都会缺少可靠依据。

### 4. TC 与 NX 状态需要严格区分

TC 能查到模板候选，不代表模型已经在 NX 中打开。前期需要明确“候选、已打开、已确认”三个状态，避免流程提前推进。

### 5. 参数处理需要更多证据支撑

零件参数设计涉及任务文本、参考公式、参数词典、NX 实际表达式等多类信息。前期如果缺少公式来源和真实表达式校验，就容易产生不可执行或不可信的写入计划。

### 6. 写入类动作需要统一确认机制

NX 参数写入、模型保存、TC 上传、TC 复制、文件覆盖等动作都会影响真实资料，必须在执行前展示确认信息，不能由智能体静默执行。

### 7. 交付物需要完整证据

设计说明书、DFMEA、截图、导出文件等交付物不能只说明“已生成”，还需要说明文件位置、文件大小、版本、校验结果和缺口处理情况。

## 五、接口模块后续优化建议

| 优化方向 | 目标 | 建议措施 |
| --- | --- | --- |
| 系统入口规则 | 让智能体先判断用户需求属于哪类系统 | 建立 IPM、QPP、ECMS/ECR、TC 的意图识别规则 |
| 字段填写规范 | 减少字段混填和无效查询 | 对责任人、任务名、项目名、变更编号、图号版本建立填写说明 |
| 查询保护 | 防止空条件和大范围查询 | 对 IPM、QPP、ECMS/ECR 增加强制或提示性条件检查 |
| 结果展示规范 | 保证用户能确认候选 | 固定任务候选表格，保留任务内容原文 |
| TC/NX 状态管理 | 防止候选对象被误认为已打开模型 | 明确候选、已打开、已确认三个状态 |
| 写入确认 | 控制真实资料风险 | 上传、覆盖、复制、保存、参数写入前展示确认表 |
| 交付证据 | 提高报告和 DFMEA 可验收性 | 输出文件路径、大小、版本、校验结果和待复核项 |

## 六、汇报结论

四大系统接口已经能够支撑零部件设计智能体的主要业务环节，但要真正稳定应用，还需要从“能调用”提升到“会判断、会追问、会展示、会确认、会留痕”。后续接口模块的优化重点，应围绕业务入口、字段规则、状态确认和交付证据展开，使智能体输出结果既能让用户看懂，也能满足后续验收和汇报要求。
